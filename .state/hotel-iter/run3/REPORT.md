**Headline:** The run-2 fix worked — the run opened and verified its way onto **booking.com's real homepage** (a first for this goal: 7 decision rows, subtask 1 verified by the noul judge at p=0.95) — and then died on the destination box: **five identical type errors on the "Where are you going?" field, no keyboard ever raised**, the two re-plans burned on wording instead of the real (mechanical) problem, and STUCK_KILL at 62 seconds after the owner card.

At 13:55:22 the cascade faced subtask 2 (reach the searchresults page), routed open-site UNCERTAIN (0.34), spent its handshake assist — whose text was *exactly right* ("…offers a destination field with placeholder text…") — stayed uncertain, and failed. **Re-plan 2** produced gen3: "Tallinn is entered as the destination in the stay search". The engine then chose fill-field HIGH (p 0.63–0.70) five steps in a row (13:55:30–43), each typing into candidate n31 "Where are you going?" and each returning **outcome=error** — frame `s-...533-0110.jpg` shows the page byte-identical and **no IME raised** after attempt #3. A stuck hint (step 6) and a stub rephrase (step 7) changed nothing; the re-plan cap was exhausted; the escalation card appeared at ~13:55:53 ("Bounded re-plans remaining: 0", frame `s-...558-0155.jpg`); the owner tapped RE-PLAN → no capacity → **STUCK_KILL 13:56:04**.

**Root cause analysis:** The blocker is no longer planning or readiness — it is **the hands**. n31 is booking.com's mobile-web destination box: exposed to the a11y tree as `tap edit` with placeholder "Where are you going?", but it is the **rich combobox class** — it does not accept programmatic text set. The executor's set-text path failed 5/5 times silently (dispatched, then errored; no keyboard, no page change, frame-proven). Everything the October battery proved (fill-field + IME submit on Google, follow-link on Wikipedia/BBC) ran on **plain inputs**; this control class accepts focus but rejects/fails the set-text action. Two compounding defects made it lethal: (1) **failure-cause-blind budgeting** — both bounded re-plans were spent refining *ladder text* (which site → how to phrase the fill subtask) when the failure was mechanical, so the writer never got the chance to change *strategy* (e.g. "activate the control, then fill the layer's own field"); (2) the identical error looped 5 times with only a hint and a stub rephrase between attempts — the loop has no mechanism rotation when a fill fails. The generalized issue: **on any travel/e-commerce-style site, the search entry is often a type-resistant custom control; the loop currently has exactly one way to type, one way to fail, and a planner that can't tell "the plan is wrong" from "the hands are wrong".**

**4 suggested solutions (with generalizability evidence):**
1. **Paste-path typing fallback** — when set-text fails on a focused editable, set the clipboard in-memory and dispatch `ACTION_PASTE`, then verify the text landed. Generalizability: this is the proven fill path for SET_TEXT-resistant inputs (it is how password managers fill); works identically on any site's combobox/rich field; goal text is not a credential, so no gate implications; small, deterministic, JVM-testable in `GestureExecutor`.
2. **Mechanism rotation per candidate** — a type error on the same candidate must never repeat identically: rotate set-text → paste → tap-then-re-observe (does a picker layer replace the field?) before the subtask may fail, and fail it *loudly with the cause class* when rotation is exhausted. Generalizability: converts the 5-identical-error loop into ≤3 informative attempts on every input class; the rotation ladder is site-agnostic by construction.
3. **Cause-aware failure routing** — mechanism-class failures (type/gesture errors) should not consume ladder re-plans: they route to in-page recovery (1+2) first, and only a strategy-level failure reaches the writer — with the 10D informed re-plan's failure block carrying the type-failure class so gen4 changes approach, not wording. Generalizability: separates "wrong plan" from "wrong hands" everywhere; the ReplanContext plumbing already exists (10D Stage 1).
4. **Sheet/unnamed-control legibility** — the run's slates carried stacks of unnamed full-width `control` nodes (a picker layer, if one opens, is currently near-invisible to the engine). Extend the 10D Stage-3 blank-label law to container-context naming for control clusters. Generalizability: every destination picker / date sheet / bottom-sheet class on mobile web.

**Recommendation:** implement **1 + 2** as one small repair (both live in the fill-field executor path; they directly attack the observed 5×-identical-error wall), and take **3** as the follow-up if run 4 shows the re-plan budget burning on mechanical failures again.

**CORRECTION (2026-10-17, post-pick code walk — owner picked 1+2+3):** solution 1's premise was **wrong**. The clipboard-paste fallback has existed since Phase 6 (`b0d113c`; `StepExecutor.enterText`: window gate → focus/click → `ACTION_SET_TEXT` → clipboard + `ACTION_PASTE` → clip hygiene) and was in the run-3 APK — meaning booking.com's destination field **rejected BOTH mechanisms, five times** (each of the 5 errors = SET_TEXT rejected, then PASTE rejected: `PASTE_FAILED`). The loop has two typing mechanisms, not one; what it lacks is exactly solutions 2+3: a third leg (tap-and-yield, letting the combobox's picker layer respond and a real input become a new candidate), never repeating a failed mechanism, and a typed cause (`INPUT_MECHANISM`) so the re-plan changes strategy. Under the owner's 1+2+3 pick, **1 becomes hardening of the existing path** (verify the text actually landed after SET_TEXT/PASTE rather than trusting the action's boolean; make the typed-field anchor and truthful cause ride the paste path), while **2 and 3 are unchanged and are the load-bearing fixes**.

**Cost:** ~$0.01–0.03 (three restructures, one assist, five batched stage-2 score calls).

Better: the docs **explicitly recommend computing your own statistic** and name exactly the two we use — **top probability** and **top-to-second ratio** — which is `Cascade.route(p, margin)` (the 10C fix). Our banding is not a misuse of confidence; it is the docs-blessed alternative, with the docs' three-band act/cautious/don't-act pattern mirrored by HIGH/UNCERTAIN/LOW and risk-scaled thresholds (the exit gate's HIGH+STRONG guard = the docs' ">0.9 before auto-executing a withdrawal" discipline).
